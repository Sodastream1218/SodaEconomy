# SodaEconomy v1.0.0

SodaEconomy 1.0.0 is the first stable public release of the production-focused Paper/Purpur economy
plugin. It combines a simple default SQLite setup with an auditable wallet transaction model and a
shared MySQL/MariaDB path for larger networks.

## Highlights

- Wallet economy with `/balance`, `/pay`, `/topbalance` and complete administrator controls
- Optional personal banking and scheduled interest
- Immutable wallet transaction history, audit/statistics and reversing rollback transactions
- SQLite, YAML and MySQL/MariaDB storage with guarded migration
- Crash-aware local asynchronous persistence and recovery WAL
- Multi-instance MySQL/MariaDB concurrency handling
- Optional Vault economy provider
- Native cached PlaceholderAPI expansion
- Persistent UUID/name identity registry with optional Floodgate classification
- Safe `/eco reload` for documented runtime settings
- Optional asynchronous GitHub Releases update checker with no auto-install and no SodaEconomy telemetry
- Public asynchronous `EconomyTransactionApi` and `PlayerIdentityApi`

## Requirements

- Paper or Purpur 1.20.2+ within SodaEconomy's supported modern API line
- Java 17-compatible plugin bytecode; use the Java runtime required by the target Paper version

## Install

1. Download `SodaEconomy-1.0.0.jar`.
2. Put it in `plugins/`.
3. Start the server once.
4. Keep SQLite for a normal single-server install, or configure MYSQL/MariaDB before intentionally
   moving to shared network storage.

Read the repository [installation guide](../installation.md) before migrating existing economy data.

## Optional integrations

Vault, PlaceholderAPI and Floodgate are optional. SodaEconomy works without them. PlaceholderAPI uses
a built-in expansion; no separate eCloud download is required.

## Known limitations / boundaries

- Folia and Spigot/Bukkit-only servers are not advertised as supported in v1.0.0.
- Vault named-bank APIs are not implemented; SodaEconomy's `/bank` system is a personal-bank model.
- Pure bank administration/interest is not represented as the same wallet-journal transaction type as
  wallet mutations; wallet↔bank transfers keep the wallet-side transaction record.
- The update checker informs only; it never downloads or installs a new JAR.
- Downgrading across schema/config changes is not generally guaranteed; keep backups before upgrades.

## Before upgrading an existing installation

Back up the active storage and `config.yml`, read `CHANGELOG.md`, and follow
[Updating and Migration](../migration.md).
